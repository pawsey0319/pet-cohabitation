# 2026-09-09 输入位置、通知入口与私聊耗时

## 本次修改

- 陪伴输入区紧跟实际对话内容。短对话不把输入框推到屏幕底部；长对话在可用高度内滚动，并继续避让键盘。
- 消息管家输入区移入其聊天卡片，接在对话下方，随页面滚动并由现有键盘输入组件定位。
- 删除消息页右上角通知按钮、未读角标以及该页为此启动的通知订阅；保留加入群聊和新建入口。
- 新版陪伴发送后即时显示主人消息。接口成功后直接显示返回的回复、结束等待；成长、形象、记忆等页面数据在后台刷新。
- Realtime 变化合并为 200 毫秒刷新，已有刷新运行时只安排一次后续刷新，降低多表状态变化引起的并行整页查询。
- `pet-chat` 返回 `Server-Timing`，区分上下文准备、生成阶段和提交；只包含耗时，不记录聊天、用户标识或模型思考内容。

## 为什么会等比较久

修复前只读取运行元数据，最近的 5 个已完成请求均标记为 `legacy`。今天其中两次耗时 35.2 秒和 60.2 秒。没有从这些记录读取用户正文，也不能据此断言特定手机已加载或未加载某次更新。

旧版省略 `mode` 时使用兼容的消息管家路径。它可能包含群消息意图判断、检索和专用回答提示；新版陪伴显式传 `companion`，只使用个人对话与允许的记忆。实际手机必须加载新的 OTA，才能使用新入口及明确的模式参数。

此外，原前端会在发送结束后等待整个异宠页面重新加载，再结束发送状态；一次状态变化还可能触发多次全量加载。本次取消回复显示对这些查询的等待。

总往返还包含网络和启动开销。生成阶段包含到模型的网络请求、生成与适配器内部恢复；旧版该阶段还覆盖管家处理，不能从这个指标单独推算模型推理时间。样例很少、对话历史不同且存在网络波动，不能据此承诺固定耗时或普遍加速比例。

直接访问本机 CPA、同样的简单陪伴提示，`glm-5.3` 有一次 4.37 秒成功结果。两个目录中可见的 Flash 路由实际均返回 HTTP 500，因此没有为了标称速度替换现有可用模型。模型列表“在线”依旧不代表对应生成请求成功。

核对 [GLM 官方思考模式说明](https://docs.z.ai/guides/capabilities/thinking-mode) 的实时正文发现，当前 GLM-5.3 系列使用强制思考，不能简单通过旧说明中的关闭参数来保证提速。本次没有依赖未验证的关闭思考参数。

## 进一步降低等待的顺序

1. 先让手机加载本次更新并使用“陪伴”，记录更接近实际使用的首条和连续对话耗时。此次 9–18 秒只是合成样例范围。
2. 若仍觉得等待明显，下一步实现流式展示，优先缩短看到第一段文字的等待。需要同时支持临时文本失效：另一客户端纠错或忘记时必须撤销旧生成，仍经过版本校验后才能提交。
3. 之后把 CPA / 临时隧道迁到持续在线、链路更短的模型服务，再对成功率、耗时和记忆质量做同样的对照。只有备选模型的实际生成与质量检查通过后再切换。

后两项尚未实现；不能把文本逐字动画当作真实流式生成，也不能把本机在线的临时方案当作长期运行保障。
