## 上一轮失败的归因与本轮隔离

上一轮 `fa6ff715-c4a2-4055-a2b9-45a31782eadc` 的 UI 场景已经走通，但末尾把 `model_runs` 与 `pet_learning_jobs` 合并检查为 0 时失败。该轮没有分别记录类型，因此保留失败状态，不回写为通过。

追踪源码发现：`app/(tabs)/me.tsx` 挂载 `useAIProviderHealth`，其 effect 自动调用 `model-health`。该函数会登记 `run_kind=text_health_check`，并通过 `checkStructuredOutput` 让真实文本模型输出固定 JSON；它并非只读健康信息。上一轮脚本没有拦截此函数，因此允许了意外健康试调用。

本轮没有把健康试调用加入豁免，而是在浏览器请求发出前返回明确的 503 测试隔离状态，保留全部模型记录为 0 的要求。捕获到 3 次自动健康请求：首次进入我的触发 2 次，换账号后触发 1 次；都没有进入服务端。服务可用性显示未知，不据此验收 AI 能力。

在浏览器打开前、进入我的后、普通群消息发送后和全部 UI 检查后，分别按**本轮合成账号/群**读取记录，仅取类型和状态：

| 检查阶段 | model_runs 总数 / run_kind | 学习任务数 / 类型 |
|---|---|---|
| 浏览器打开前 | 0 / 空 | 0 / 空 |
| 我的页面挂载后 | 0 / 空 | 0 / 空 |
| 普通群聊发送后 | 0 / 空 | 0 / 空 |
| 完成 UI 检查后 | 0 / 空 | 0 / 空 |

群内参与在合成数据中关闭，未开启观察或关系学习授权。新轮结果未发现越权学习。旧轮账号已删除，不能把新轮零记录冒充旧轮的精确分类；健康检查归因基于源码和自动请求复现。

## 清理与限制

本轮先清除有精确合成账号/群归属的模型日志，再删除群、三个 Storage 对象和两个 Auth 账号，最后核对 profiles 不存在；所有步骤成功。

旧轮清理仅删除 Auth 账号，而 `model_runs.owner_id` 使用 `ON DELETE SET NULL`，可能留下已脱离账号的健康运行日志。旧脚本未记录运行 ID，无法在不影响其他账号日志的前提下精确定位，因此没有泛查或删除无主日志。此限制已报告整合负责人，新脚本已修正清理顺序。
